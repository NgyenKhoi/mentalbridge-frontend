## 2. Decisions Not Yet Approved by Owner (`[PENDING_OWNER_APPROVAL]`)

1. **No Stitch UI Capture for MB-703:** `mobile/.stitch/` contains `MB-654` and `MB-720` only; there is no owner-approved Stitch design for MB-703 native locked preview or checkout card. Implementation reuses approved MB-671 Vietnamese copy semantics (`LockedPlanPreview.tsx`, `PlanUpgradeContinue.tsx`) and `MB-611` theme tokens (`@/theme/tokens`), pending UI/Stitch sign-off.
2. **Primary In-App VietQR Graphic vs Text Transfer Details + Hosted PayOS Fallback:** Consultation ADR 0047 defines in-app VietQR (`qrCode`, `bin`, `accountNumber`, `accountName`, `amount` / `amountVnd`, `description`, `expiredAt` / `expiresAt`) as primary `PAYOS` checkout and `https://pay.payos.vn/...` `checkoutUrl` as optional fallback. Because `/mobile/package.json` is owner-controlled (`CODEOWNERS`) and contains no QR SVG rendering package (`react-native-svg`/`qrcode`) and no clipboard library, MB-703 displays selectable VietQR bank-transfer text fields with an explicit disclaimer that no scannable QR image is rendered in-app yet, plus an optional strictly-allowlisted HTTPS PayOS fallback button (`pay.payos.vn` only; blocked for `FAKE` and dormant `MOMO`). Adding a native QR renderer package requires owner dependency approval.
3. **Web-to-App Subscription Return Deep Link:** No owner-approved mobile return deep link or web handoff contract exists yet for returning from `pay.payos.vn` directly back into the Android app, and `origin` is strictly in-memory within the session (after an Android process kill, re-entry validates entitlement/payment fresh and falls back cleanly without claiming `origin` restoration). Re-entry relies on `AppState` foreground focus refresh plus manual `"Kiểm tra lại thanh toán"`.
4. **Upgrade Return Landing Behavior when Coming from Guide:** Automatically opening Care Plan proposal vs showing explicit `"Tiếp tục tới Kế hoạch hỗ trợ"` confirmation card (matching MB-671 `PlanUpgradeContinue`) uses explicit confirmation CTA so MB-703 never auto-creates/auto-activates a Plan without consent; exact transition UX is pending owner review when wiring MB-701 + MB-702 + MB-703.

## 3. Verified Technical Blockers (Staging / Infrastructure / Unmerged PRs)

1. **Unmerged Upstream PRs (#266 MB-701, #292 MB-702):** Neither `AssessmentJourneyScreen.tsx` nor `SupportPlanActionWorkspace.tsx` is merged into `origin/dev`, and `/mobile/src/app/` is protected by `.github/CODEOWNERS`. MB-703 therefore delivers an isolated `mobile/src/support-plan-access/` boundary (`SupportPlanAccessGate` + hooks + API adapter + contract) with zero edits to PR #266 / #292 / `CODEOWNERS` paths.
2. **PayOS Return URLs Locked to Staging Web Origin:** `BillingProperties.java` requires `payosReturnUrl` and `payosCancelUrl` to use `https://staging.mentalbridge.online`. No `mentalbridge://` callback or Android App Link (`intentFilters`) exists in backend Consultation or `mobile/app.json`.
3. **No `EXPO_PUBLIC_WEB_BASE_URL` Contract:** Per `MB-611_MOBILE_DELIVERY_CONTRACT_V1.md`, mobile builds expose only `EXPO_PUBLIC_API_BASE_URL` and `EXPO_PUBLIC_API_TIMEOUT_MS`. MB-703 must not invent web checkout URLs.
4. **Staging Edge Routing & Physical Android Verification Pending:** Mobile currently exercises `GET /api/v1/service-credits` only (`appointment-api.ts`). Live staging gateway exposure of `/api/v1/service-plans`, `/api/v1/subscriptions/checkout`, and `/api/v1/payments*`, as well as PayOS external browser return on physical Android (`MB-666`), remain unverified in dev/local unit tests and must not be marked passed until staged E2E runs.

## 4. Post-Merge Integration Boundary (`MB-701` & `MB-702`)

Once PR #266 (`MB-701`) and PR #292 (`MB-702`) are merged into `dev`, wire MB-703 at two explicit boundaries without duplicating entitlement/payment logic:

1. **`SupportPlanActionWorkspace.tsx` (`MB-702`, tracked by `CARE_OWNERSHIP_INTEGRATION_BLOCKER`):**
   - Replace the temporary `autoProposal === 'locked'` / `activationLocked` plain fallback text with `<SupportPlanAccessRoute ...>` or `<SupportPlanAccessGate ...>` wrapping locked proposal entry.
   - Bind Care ownership through `createCareOwnershipAdapter(services.api, { subject: session.subject, getActiveSubject: () => currentSubject, getSessionGeneration: () => sessionGeneration })` wrapping MB-702's `createSupportPlanActionApi(client)` (`getCurrent()`, `getDraft()`, `getHistory()`), where `client` is the single authenticated `AxiosInstance` (`createApiClient({ config: runtimeConfig, getBearerToken: () => secureCredentialStore.getAccessToken() })`) inside `SupportPlanRoute.tsx` / `AccountSupportPlanAccessBoundary`.
   - Respect `context.accessMode` (`'read-only-owned'` hides/disables create/activate CTA while keeping owned Plans/history readable; `'full-create-and-read'` enables proposal/activation). Keep `SupportPlanActionWorkspace` owning Care `POST /api/v2/support-plans` and activation ONLY after the user explicitly chooses to proceed from `upgrade-confirmed` or verified `owned-plan`.
2. **`AssessmentJourneyScreen.tsx` (`MB-701`):**
   - When Guide `nextAction` lands on SupportPlan while Consultation entitlement is locked (`EXPLORE_GUIDE_RESOURCES` or navigating into `./support-plan` preview), pass `origin={{ source: 'GUIDE', guideId, step }}` into `SupportPlanAccessRoute` / `SupportPlanAccessGate` so users can inspect the 14-day example preview, upgrade via PayOS, return to verify Plus status, and keep Guide navigation intact without triggering auto-proposal.
   - When `nextAction === 'REVIEW_SAFETY_SUPPORT'`, pass `safetyOverride={true}` (or keep Safety card prioritized) so paywall/upgrade UI is completely suppressed.
