# MB-774 Mầm reward reads

Scope: web only. No backend, contract, `.tsx` or `.css` change. Authority: `docs/ADR_MAM_RIVE_V1_CONTRACT.md` (reward watcher, baseline, reconciliation, 5 min freshness) and backend ADR 0036 (the `VISIBLE`/`HIDDEN` preference covers XP rewards; Bingo has no hide control on web).
The MB-773 director is unchanged. MB-774 only feeds it.

## Privacy

No award data leaves the device: the reads are the owner's own existing requests; the event stays in `window` and the director's per-account `localStorage` record. A read answers only for the dock session that started it: each publisher takes `mamAwardSession()` before its request and dispatches only if it is unchanged, and the dock listener's cleanup (unmount or account change) ends the session. A response that lands after logout or an account switch never reaches the next account's record (`mam-award-session.ts`; regression in `use-mam-celebrations.test.tsx`). The storage key and record shape are unchanged. Reduced-motion and mute behaviour is inherited from MB-773.

## Existing E2E adjusted

- `mam-celebrations.spec.ts`: the host now reads the gallery itself. The `/achievements` mock lists the achievements the scenario queues (an empty read would reconcile them away, which is the intended director behaviour), and the scenarios wait until the director has reconciled the domain before the fake baseline.
- `resources.spec.ts` and `achievements.spec.ts` are unchanged and pass.

## Known limits

- Bingo is read only by the Resources page (plan sync, self-confirmation), so a Bingo celebration needs the user to open `/resources`; the reader does not poll it. This keeps free accounts, which have no plan board, out of the Bingo endpoint.
- A NONE plan state still syncs and dispatches the returned board (Content retires it without exposing it); the director sees it as a board read.
- The MB-773 named follow-ups (mixed-scope retry, midnight retry, session liveness) are not part of this story. A focus read re-evaluates the budget, so focus now retries naturally.
- The "removed before release" state is not driven by E2E: it needs a second read inside the 10 s window, which has no UI trigger. It is covered by the director's unit tests.
